# Лабораторная работа №11
## Исследование неблокирующего режима сокетов

**Цель работы:** изучить неблокирующие вызовы сокетов, обработку отсутствия подключений и данных, а также затраты процессора на постоянный опрос.

**Среда:** Windows, Python 3.

## Файлы

- nonblocking_server.py — неблокирующий TCP-сервер.
- nonblocking_client.py — клиент с паузами перед подключением и отправкой данных.

Обе программы используют адрес 127.0.0.1 и порт 9995. В клиенте исправлена опечатка задания: порт 995 заменён на 9995 для соответствия серверу.

## Запуск

В первом окне cmd:

    python nonblocking_server.py

Во втором окне cmd:

    python nonblocking_client.py

## Результаты эксперимента

При отсутствии подключения сервер печатал точки. После подключения клиента точки сменились звёздочками: сервер ожидал данные. Затем он получил строку Hello from non-blocking test и завершился.

В исследовательской части первая строка time.sleep(0.01), расположенная в обработчике исключения при accept(), была закомментирована. Пауза в цикле recv() сохранена.

Во время ожидания клиента Диспетчер задач показывал около 4% CPU у процесса Python. Постоянная загрузка одного логического процессора на 100% не наблюдалась. После запуска клиента обмен данными успешно завершился.

В репозитории сохранён исследовательский вариант сервера с закомментированной первой паузой.

## Ответы на контрольные вопросы

### 1. Что означает EWOULDBLOCK / EAGAIN?

Этот код сообщает, что операция сейчас не может завершиться немедленно: для accept() ещё нет ожидающего подключения, а для recv() пока нет доступных данных.

В Windows аналогичное состояние обозначается WSAEWOULDBLOCK. Python представляет его исключением BlockingIOError.

Поскольку сокет переведён в неблокирующий режим вызовом setblocking(False), ядро возвращает управление программе вместо ожидания. Программа сама определяет, что делать дальше.

### 2. Почему удаление time.sleep(0.01) увеличивает нагрузку?

Без паузы цикл постоянно повторяет accept(), хотя новых подключений нет. Каждая попытка требует обращения к сетевой подсистеме ОС, проверки очереди, возврата результата и обработки исключения в Python.

При системном вызове процессор переходит из пользовательского режима в режим ядра и затем обратно. Такой переход не обязательно означает переключение на другой поток, но всё равно требует работы процессора. Дополнительные затраты создаёт постоянная печать точек с flush=True.

Процессор занят повторением безрезультатных операций. Поэтому нагрузка может приближаться к полной загрузке одного логического процессора.

В данном эксперименте у процесса наблюдалось около 4% общей мощности CPU. Показание зависит от числа логических процессоров, планирования потоков и затрат на вывод в терминал. Указанные в задании постоянные 100% на одном логическом процессоре не были зафиксированы.

### 3. Как эту проблему решают промышленные серверы?

Вместо непрерывного опроса каждого сокета сервер использует уведомления операционной системы.

В Linux механизм epoll позволяет ожидать готовности множества сокетов. Поток пробуждается, когда появляются события, например новое подключение или данные для чтения.

В Windows IOCP позволяет получать уведомления о завершении асинхронных операций ввода-вывода.

Благодаря этому сервер может обслуживать много соединений, не расходуя процессорное время на постоянные пустые проверки. Такие механизмы используются в системах обработки событий, на которых строятся nginx и Node.js.
